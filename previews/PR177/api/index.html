API

Options

Keyword arguments of plan_nfft, plan_rnfft, plan_nfct and plan_nfst; plan_nnfft takes them without tilesize and measure, its dims is the dimension of the sources in an array of the size given as third argument, and its window, W and σ apply to its inner NFFT:

keywordmeaning
reltolrequested relative error, default 1e-8
dimsdimensions to transform, see Transforms along Dimensions
eltypeFloat32 or Float64, default from the nodes
storagearray type of data and workspace, default from the nodes; see GPU
nthreadsnumber of threads, default Threads.nthreads()
window:auto, KaiserBessel(), ExpSemicircle(), CustomWindow(φ)
W, σwindow width and oversampling factor
fftFFT backend, default FFTWBackend()
tilesizeedge length of the tiles the nodes are sorted into (expert option)
measuretrue: time the four parameter sets of lowest predicted cost at plan time and keep the fastest (CPU)

The first five are part of the Abstract Interface and mean the same for every implementation; the others are specific to NFFT.jl. An unknown option is an error, and so are fft, tilesize and measure for plans on a GPU. How to use window, W, σ and fft is shown in Choosing Parameters.

Plans and transforms

AbstractNFFTs.plan_nfft — Function
plan_nfft([backend,] k, N; reltol=1e-8, dims=:, eltype, storage, nthreads, kwargs...)

Plan an NFFT for the nodes k (a d × J matrix, or a vector for d = 1, entries in [-1/2, 1/2)) and an equidistant array of size N (an integer or a tuple; with dims, the size of the whole array including batch dimensions). Without backend the active backend is used.

Generic options, accepted by every implementation:

  • reltol: requested relative error (ℓ² norm over random data)
  • dims: dimensions to transform (:, an integer or a contiguous range); the other dimensions are batch dimensions and pass through unchanged
  • eltype: real element type of the data, default float(eltype(k))
  • storage: array type of data and workspace, default the array type of k
  • nthreads: number of CPU threads, default Threads.nthreads()

Further keyword arguments are specific to the implementation; an implementation throws an ArgumentError for options it does not know.

AbstractNFFTs.plan_nnfft — Function
plan_nnfft([backend,] k, y[, N]; kwargs...)

Plan an NNFFT with non-equidistant nodes k (D × J) in the frequency domain and y (D × M) in the spatial domain. The input is a vector of length M, or an array of size N whose dimension dims (an integer) holds the M sources; the output has the J targets in that dimension, and the other dimensions are batch dimensions. Keyword arguments as for plan_nfft.

AbstractNFFTs.plan_rnfft — Function
plan_rnfft([backend,] k, N; kwargs...)

Plan an NFFT with real values at the nodes k (in [-1/2, 1/2)) for an array of logical size N (the NFFT counterpart of FFTW's brfft/rfft). The input of the direct transform is the half h of the coefficients with n₁ = 0 … N₁÷2, an array of size (N₁÷2+1, N₂, …) whose other dimensions are indexed as in plan_nfft; the direct transform is

f̂_j = Re Σ_n h_n exp(-2πi n·k_j),

the adjoint maps real values y at the nodes to h_n = Σ_j y_j exp(2πi n·k_j). The two are adjoint with respect to the real inner product. With dims, the first of the transformed dimensions is the halved one. Keyword arguments as for plan_nfft.

NFFT.NFFTPlan — Type
NFFTPlan{T,D,R}

NFFT plan of NFFT.jl, created by plan_nfft(k, N; kwargs...) or NFFTPlan(k, N; kwargs...).

Generic options (every AbstractNFFTs implementation): reltol (default 1e-8), dims, eltype, storage, nthreads. Options of NFFT.jl:

  • window: :auto (default; all windows with a parameter table compete), KaiserBessel(), ExpSemicircle() or a CustomWindow (needs W and σ)
  • W: window width (integer, odd allowed; W = 2m in the notation of Knopp et al. 2023)
  • σ: oversampling factor
  • fft: FFT backend, default FFTWBackend()
  • tilesize: expert option, tile edge of the node binning
  • measure: true times the four parameter sets of lowest predicted cost at plan time (transform and adjoint) and keeps the fastest; the cost model cannot see how fast FFTW is for a particular grid size

T is the real element type, D the number of dimensions of the array and R that of the output (1 without batch dimensions). The compiler infers the type of the plan when dims is left out or a single dimension; with a range it depends on its length.

NFFT.NFCTPlan — Type
NFCTPlan{T,D,R}
NFSTPlan{T,D,R}

NFCT and NFST plans of NFFT.jl, created by plan_nfct(k, N; kwargs...) and plan_nfst(k, N; kwargs...), with the definitions of NFFT3: for nodes k in [0, 1/2]^d and a real array f of size N,

NFCT: f̂_j = Σ_{n=0}^{N-1} f_n Π_d cos(2π n_d k_dj),   NFST: f̂_j = Σ_{n=1}^{N} f_n Π_d sin(2π n_d k_dj)

(the array index of mode n is n + 1 for the NFCT and n for the NFST). transpose(p) is the transposed transform. Options as for NFFTPlan; batch dimensions run as slices, in parallel or one after the other.

NFFT.NNFFTPlan — Type
NNFFTPlan{T,D,M}

NNFFT plan of NFFT.jl (non-equidistant nodes in both domains), created by plan_nnfft(k, y[, N]; kwargs...) for targets k (D × J) and sources y (D × N), arbitrary real coordinates:

f̂_j = Σ_l f_l exp(−2πi k_j·y_l)

The cost grows with the product of the extents of k and y (the size of the inner NFFT is about 4σ²·Y·K per dimension), not with their numbers. With an array size N (M dimensions), dims selects the dimension of the sources; the transform maps it to the targets and passes the other dimensions through, one slice after the other. Generic options reltol, eltype, storage, nthreads; restrictions of the inner NFFT window (:auto, KaiserBessel() or ExpSemicircle()), W and σ, and its FFT backend fft, as for NFFTPlan.

Windows and FFT

NFFT.AbstractWindow — Type
AbstractWindow

Window function of the NFFT. A window is evaluated in grid units, φ(z) for z ∈ [-W/2, W/2] (W the window width, W = 2m in the notation of Knopp et al. 2023); it is symmetric and zero outside. The resampling evaluates a piecewise polynomial fitted to φ, so the cost of φ itself does not matter.

Families with a parameter table (used by the automatic parameter choice): KaiserBessel, ExpSemicircle. Any other window can be used with explicit W and σ through CustomWindow.

source
NFFT.KaiserBessel — Type
KaiserBessel()

Continuous Kaiser–Bessel window (Potts & Tasche 2021): the sinh form sinh(β√(1−(2z/W)²))/√(1−(2z/W)²) minus its edge value β, so that it vanishes at |z| = W/2. The shape parameter β is taken from the kernel table (optimised per W and σ).

source
NFFT.ExpSemicircle — Type
ExpSemicircle()

Exponential of semicircle family, φ(z) = exp(β((1−(2z/W)²)^e₀ − 1)). e₀ = 1/2 is the ES kernel of FINUFFT (Barnett et al. 2019); a free exponent e₀ is the family used by ducc (Arras et al. 2021). β and e₀ are taken from the kernel table.

source
NFFT.CustomWindow — Type
CustomWindow(φ)

User-defined window: φ(z, W) must be symmetric in z and zero for |z| ≥ W/2. Requires explicit W and σ in the plan.

source
NFFT.AbstractFFTBackend — Type
AbstractFFTBackend

FFT used for the oversampled grid. A backend must provide in-place batched 1D transforms along a chosen dimension of an array view (forward and unnormalised backward).

source
NFFT.FFTWBackend — Type
FFTWBackend(; flags = FFTW.ESTIMATE)

FFTW on the CPU. In D ≥ 2 NFFT.jl threads the per-dimension passes itself over single-threaded FFTW plans: FFTW's own threading with ESTIMATE produces plans up to 17× slower than MEASURE, while single-threaded batched ESTIMATE plans are within 10–20 % of MEASURE. A transform with one dimension uses FFTW's own threading.

NFFTTools

NFFTTools.sdc — Function
weights = sdc(p::AbstractNFFTPlan; iters = 20)

Sampling density compensation weights for the nodes of the NFFT plan p, computed with iters iterations of the method of Pipe and Menon (Magn Reson Med 41(1):179–186, 1999, doi:10.1002/(SICI)1522-2594(199901)41:1<179::AID-MRM25>3.0.CO;2-V). The iteration uses the resampling stage of the plan, i.e. the window function on the oversampled grid, as its kernel. The weights therefore depend on the window of the plan rather than on its accuracy: narrow windows give better weights than wide ones. With NFFT.jl, plan_nfft(k, N; W = 4, σ = 2.0) works well (MRI test data: 0.11 relative deviation of a gridding reconstruction from the scanner's, 0.21 with the window chosen for reltol = 1e-3).

The weights are real, positive and scaled such that $A^{\mathsf{H}} \operatorname{diag}(w) A \bm{1} ≈ \bm{1}$. For nodes on the equidistant grid of an array of size N they are ≈ 1/prod(N).

p must be a plan without batch dimensions that implements the stage interface of AbstractNFFTs (oversampled_size, resampling!, resampling_adjoint!).

source

NFFTTools.calculateToeplitzKernel — Function
calculateToeplitzKernel(shape, tr::AbstractMatrix{T}; fftplan = plan_fft(zeros(Complex{T}, 2 .* shape); flags=FFTW.ESTIMATE), kwargs...)

Calculate the kernel for an implementation of the Gram matrix $A^{\mathsf{H}} A$ that utilizes its Toeplitz structure. The output is an array of twice the size of shape, as the Toeplitz trick requires an oversampling factor of 2 (cf. Wajer, F. T. A. W., and K. P. Pruessmann. "Major speedup of reconstruction for sensitivity encoding with arbitrary trajectories." Proc. Intl. Soc. Mag. Res. Med. 2001.). The type of the kernel is Complex{T}, i.e. the complex of the k-space trajectory's type; for speed and memory efficiency, call this function with Float32.(tr), and the kernel will also be Float32.

The kernel is computed with an adjoint NFFT of the active AbstractNFFTs backend (e.g. NFFT.jl after using NFFT).

Required Arguments

  • shape::NTuple(Int): size of the image; e.g. (256, 256) for 2D imaging, or (256,256,128) for 3D imaging
  • tr::Matrix{T}: non-Cartesian k-space trajectory in units revolutions/voxel, i.e. tr[i] ∈ [-0.5, 0.5] ∀ i. The matrix has the size 2 x Nsamples for 2D imaging with a trajectory length Nsamples, and 3 x Nsamples for 3D imaging.

Keyword Arguments:

  • fftplan: plan for the final FFT of the kernel from image to k-space. Therefore, it has to have twice the size of the original image. default = plan_fft(zeros(Complex{T}, 2 .* shape); flags=FFTW.ESTIMATE). If this constructor is used many times, it is worth to precompute the plan with plan_fft(zeros(Complex{T}, 2 .* shape); flags=FFTW.MEASURE) and reuse it.
  • kwargs: passed on to plan_nfft, e.g. reltol for the accuracy of the kernel.

Examples

julia> using NFFT, NFFTTools

julia> Nx = 32;

julia> trj = Float32.(rand(2, 1000) .- 0.5);

julia> λ = calculateToeplitzKernel((Nx, Nx), trj);

julia> y = randn(ComplexF32, Nx, Nx);

julia> convolveToeplitzKernel!(y, λ);
source
NFFTTools.calculateToeplitzKernel! — Function
calculateToeplitzKernel!(f::AbstractArray{Complex{T}}, p::AbstractNFFTPlan, tr::AbstractMatrix{T}, fftplan)

Calculate the kernel for an implementation of the Gram matrix that utilizes its Toeplitz structure and writes it in-place in f, which has to be twice the size of the desired image matrix, as the Toeplitz trick requires an oversampling factor of 2 (cf. Wajer, F. T. A. W., and K. P. Pruessmann. "Major speedup of reconstruction for sensitivity encoding with arbitrary trajectories." Proc. Intl. Soc. Mag. Res. Med. 2001.). The type of the kernel f has to be Complex{T}, i.e. the complex of the k-space trajectory's type; for speed and memory efficiecy, call this function with Float32.(tr), and set the type of f accordingly.

Required Arguments

  • f::AbstractArray{Complex{T}}: array in which the kernel will be written.
  • p::AbstractNFFTPlan: NFFT plan for an array of twice the image size; its nodes are set to tr.
  • tr::Matrix{T}: non-Cartesian k-space trajectory in units revolutions/voxel, i.e. tr[i] ∈ [-0.5, 0.5] ∀ i. The matrix has the size 2 x Nsamples for 2D imaging with a trajectory length Nsamples, and 3 x Nsamples for 3D imaging.
  • fftplan: plan for the final FFT of the kernel from image to k-space. Therefore, it has to have twice the size of the original image. Calculate, e.g., with fftplan = plan_fft(zeros(Complex{T}, 2 .* shape); flags=FFTW.MEASURE), where shape is the size of the reconstructed image.

Examples

julia> using NFFT, NFFTTools, NFFTTools.FFTW

julia> Nx = 32;

julia> trj = Float32.(rand(2, 1000) .- 0.5);

julia> p = plan_nfft(trj, (2Nx, 2Nx));

julia> fftplan = plan_fft(zeros(ComplexF32, (2Nx,2Nx)); flags=FFTW.MEASURE);

julia> λ = Array{ComplexF32}(undef, 2Nx, 2Nx);

julia> calculateToeplitzKernel!(λ, p, trj, fftplan);

NFFTTools.convolveToeplitzKernel! — Function
convolveToeplitzKernel!(y::AbstractArray{T,N}, λ::AbstractArray{T,N}[, fftplan = plan_fft(λ; flags=FFTW.ESTIMATE), ifftplan = plan_ifft(λ; flags=FFTW.ESTIMATE), xOS1 = similar(λ), xOS2 = similar(λ)])

Convolves the image y with the Toeplitz kernel λ and overwrites y with the result. y is also returned for convenience. As this function is commonly applied many times, it is highly recommended to pre-allocate / pre-compute all optional arguments. By doing so, this entire function is non-allocating.

Required Arguments

  • y::Array{T,N}: Input image that will be overwritten with the result. y is a matrix (N=2) for 2D imaging and a 3D tensor (N=3) for 3D imaging. The type of the elements T must match the ones of λ.
  • λ::Array{T,N}: Toeplitz kernel, which has the same element type as y and twice its size due to the required oversampling (cf. calculateToeplitzKernel).

Optional, but highly recommended Arguments

  • fftplan: plan for the oversampled FFT, i.e. it has to have twice the size of the original image. Calculate, e.g., with fftplan = plan_fft(λ; flags=FFTW.MEASURE).
  • ifftplan: plan for the oversampled inverse FFT. Calculate, e.g., with ifftplan = plan_ifft(λ; flags=FFTW.MEASURE).
  • xOS1: pre-allocated array of the size of λ. Pre-allocate with xOS1 = similar(λ).
  • xOS2: pre-allocated array of the size of λ. Pre-allocate with xOS2 = similar(λ).

Examples

julia> using NFFT, NFFTTools, NFFTTools.FFTW

julia> Nx = 32;

julia> trj = Float32.(rand(2, 1000) .- 0.5);

julia> λ = calculateToeplitzKernel((Nx, Nx), trj);

julia> xOS1 = similar(λ);

julia> xOS2 = similar(λ);

julia> fftplan = plan_fft(xOS1; flags=FFTW.MEASURE);

julia> ifftplan = plan_ifft(xOS1; flags=FFTW.MEASURE);

julia> y = randn(ComplexF32, Nx, Nx);

julia> convolveToeplitzKernel!(y, λ, fftplan, ifftplan, xOS1, xOS2);

NDCTPlan(k, N)
NDSTPlan(k, N)
NNDFTPlan(k, y)

Direct evaluation of the NDFT, NDCT, NDST and NNDFT with the definitions of the fast plans (O(J·prod(N)) operations), as a reference for tests and small problems. Nodes are a D × J matrix or, for D = 1, a vector; the sums are computed in double precision.

AbstractNFFTs.AbstractRNFFTPlan — Type
AbstractRNFFTPlan{T,D,R}

Abstract type for an NFFT plan with real values at the nodes (the NFFT counterpart of FFTW's brfft/rfft): the direct transform maps the half n₁ ≥ 0 of the complex coefficients to real values at the nodes, the adjoint maps real values at the nodes to that half.

  • T is the real element type (Float32/Float64)
  • D is the number of dimensions of the input array.
  • R is the number of dimensions of the output array.

AbstractNFFTs.GenericOptions — Type
GenericOptions

The options every implementation of the interface accepts, resolved from the keyword arguments of plan_nfft and friends by generic_options:

  • reltol: requested relative error (ℓ² norm over random data)
  • dims: dimensions of the transform (a contiguous range); all other dimensions are batch dimensions that pass through unchanged
  • eltype: real element type of the data (Float32, Float64, …)
  • storage: array type of the data and the workspace (Array, a GPU array type, …)
  • nthreads: number of CPU threads
